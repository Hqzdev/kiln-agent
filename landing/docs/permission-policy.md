# Kiln: как выдаются разрешения

Задача: P0.5. Дата: 11 октября 2026.

## Основное правило

Сервер на Java проверяет право на действие дважды: перед подготовкой инструмента и прямо перед выполнением. Интерфейс, способ подключения, инструкция модели, навык или сообщение коллеги не могут обойти эту проверку.

При добавлении проекта пользователь разрешает доступ к выбранным папкам. После этого чтение файлов внутри них не требует вопроса на каждый файл. Для изменения файлов, запуска команд и действий во внешних системах нужно отдельное разрешение: одноразовое или заранее выданное правило с явными ограничениями.

## Что входит в разрешение

| Поле | Что ограничивает |
| --- | --- |
| projectId | Проект, в котором можно действовать |
| capability | Конкретный инструмент и вид действия |
| role / session | Роли или сессии, которым разрешено действие |
| path roots | Разрешённые папки с проверенными фактическими путями |
| branch / remote / refspec | Ветку, удалённый репозиторий и точное направление передачи Git |
| preparedActionHash | Контрольный отпечаток неизменных аргументов и содержимого действия |
| expiresAt / usesRemaining | Срок действия и оставшееся число применений |
| grantedBy | Проверенного пользователя, который выдал разрешение |

Одноразовое разрешение относится к конкретному hash. Повторное правило разрешает определённый вид действий в заданных пределах. Похожее действие за пределами правила требует нового запроса.

## Защита основных веток

Изменения `refs/heads/main` и основной ветки удалённого репозитория запрещены всегда. Основная ветка защищена и тогда, когда называется не main.

Проверка охватывает полную запись передачи Git (`refspec`), исходную и конечную ссылки, `git -C`, работу без выбранной ветки (`detached HEAD`), merge/reset/rebase, прямое изменение ссылок и общие служебные данные Git. Это закрывает обходы через другие команды.

Разрешение на рабочую ветку не снимает запрет. Интерфейс объясняет причину отказа, а сервер блокирует выполнение.

## Сохранение и отправка изменений

Commit сохраняет изменения в локальной истории. Push отправляет их в удалённый репозиторий. Для них нужны разные разрешения.

1. Подготовить список файлов для коммита, изменения, ветку и исходный коммит base SHA.
2. Запросить разрешение на конкретный PreparedCommit.
3. Ещё раз проверить hash, состояние репозитория и разрешение; выполнить commit один раз.
4. Сохранить номер коммита (SHA) и подтверждение операции.
5. Подготовить push: удалённый репозиторий, источник и все конечные ссылки.
6. Запросить отдельное разрешение на push и повторно проверить защиту веток.
7. Сохранить подтверждённое состояние удалённого репозитория. Если исход неизвестен, сначала выяснить, что произошло.

## Отказы, отмены и одновременные решения

- `denied`: пользователь отказал; действие не начинается, причина остаётся в истории.
- `revoked` / `expired`: разрешение отозвано или просрочено; новые операции запрещены.
- Изменились hash, base SHA или аргументы: разрешение становится `invalidated`, нужно новое решение.
- Mac и iPhone ответили одновременно: сервер принимает только одно решение как неделимое действие.
- Телефон без связи: устаревшее решение об опасном действии не ставится в очередь для автоматического выполнения.
- Агент пытается разрешить действие сам себе: сервер отказывает. Решение может отправить только доверенный пользовательский клиент.

## Примеры

| Ситуация | Результат |
| --- | --- |
| Чтение внутри уже разрешённой папки проекта | Разрешено |
| Новый путь снаружи, в том числе через символическую ссылку | Отказ или запрос расширения доступа |
| Commit в рабочей ветке без разрешения | Ожидание разрешения |
| Push при наличии только разрешения на commit | Ожидание отдельного разрешения на push |
| Изменения поменялись после одобрения | Старое разрешение недействительно |
| Повтор действия в пределах выданного правила | Разрешено, пока действуют срок и счётчик |
| Push в main или основную ветку | Запрещено при любом разрешении |
| Модель просит повысить свои права | Запрещено |

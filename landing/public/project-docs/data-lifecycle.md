# Blot: где хранятся данные и как их удалить

Задача: P0.9. Дата: 11 октября 2026.

## Где лежат данные

`installationId` в путях — идентификатор конкретной установки Blot. Данные хранятся отдельно от файлов самого приложения.

| Данные | Место хранения | Особенности |
| --- | --- | --- |
| База SQLite | Application Support/Blot/<installationId>/database | Вне пакета приложения |
| Результаты работы и файлы | Application Support/Blot/<installationId>/artifacts | Контрольный отпечаток содержимого и описание записаны в базе |
| Точки восстановления работы | Та же база | Записываются согласованно с журналом операций |
| Диагностические записи | Application Support/Blot/<installationId>/logs | Старые файлы заменяются, секреты удаляются из записей |
| Ключ GigaChat и секреты устройств | Keychain | Не входят в обычный экспорт истории |
| Память пользователя | SQLite в Application Support/Blot/<installationId>/database | Локальна для установки на Mac, отделена от памяти проектов; Markdown доступен для экспорта и просмотра |
| Репозиторий пользователя | Выбранная пользователем папка | Не является частью хранилища Blot |
| Кэш и черновики iOS | Изолированное хранилище приложения на iPhone | Есть отметка устаревания и позиция последнего принятого события |

## Как данные меняются

Объект, его версия и событие для отправки клиентам записываются согласованно. Каждое событие получает постоянный ID и порядковый номер. Копию результата (`ArtifactSnapshot`) нельзя менять задним числом. Новое содержимое получает новый hash — контрольный отпечаток — и может сделать прежнее ревью или разрешение недействительным.

У записи памяти есть источник, автор, версия и отметка актуальности. Предположения не выдаются за факты. Память проекта доступна только в его пределах. Память пользователя хранится отдельно на Mac и не переносится в проекты автоматически; в запрос модели попадают только выбранные по релевантности записи.

## Восстановление после сбоя

До действия, которое меняет файлы или внешнюю систему, сохраняются его точное описание (`PreparedAction`) и запись в журнале. Точка восстановления содержит версию плана, активные попытки, входящие сообщения и позицию в потоке событий.

После сбоя система восстанавливает известное состояние. Если исход операции неизвестен, она сначала проверяет Git или запущенный процесс. Повтор без такой проверки запрещён.

Полная копия состояния (`snapshot`) содержит номер последнего учтённого события (`watermark`). Если старых событий уже недостаточно для восстановления, клиент получает новую копию. Повторная доставка события не создаёт второе сообщение или операцию инструмента.

## Срок хранения

Проекты, принятые результаты и материалы проверок хранятся до явного удаления пользователем. Архивирование убирает завершённую работу из активного списка, но сохраняет связи и доступ к источникам.

Начальный лимит логов — восемь файлов по 8 MiB. При замене старых файлов удаляется только диагностика, а обязательные материалы принятого результата сохраняются. Настройку нужно проверить в J13.14.

Временный кэш можно очищать, только если все актуальные ссылки остаются рабочими. Если место на диске закончилось, новые изменения останавливаются. Пользователю предлагается выбрать очистку или увеличение лимита.

## Резервная копия и экспорт

Резервная копия SQLite должна учитывать WAL — журнал ещё не перенесённых в основной файл изменений. Копирование одного файла открытой базы не считается корректной резервной копией.

Копия включает описание состава (`manifest`): версию структуры базы, версии сборок, ID и hash результатов. При восстановлении проверяются все ссылки.

Экспорт проекта содержит требования, план, сообщения, память, ревью и материалы проверок. Из диагностического экспорта удаляются секреты и данные доступа. Обычный экспорт не передаёт ключ провайдера или секрет доверенного устройства.

## Удаление

Удаление проекта в Blot не удаляет исходный репозиторий пользователя и ссылки в удалённом Git. Сначала останавливаются сессии и отзываются разрешения проекта, затем удаляются поисковые индексы, записи и неиспользуемые файлы результатов. Перед очисткой итог должен отражать внешние операции с неизвестным исходом.

Отзыв устройства запрещает ему новые команды и подписки на события, но история его действий сохраняется. Удаление записи памяти очищает связанные поисковые индексы и исключает её из последующих запросов. Пользовательская память удаляется отдельно от проектной; Markdown-экспорт не является источником для автоматической подстановки в модель. Данные других проектов и общие ключи провайдера не удаляются вместе с одной записью.

## Что проверено в документе

Описана цепочка: проект → запуск → копия результата → ревью → архив → экспорт → восстановление → удаление. Для каждого этапа определено, кто отвечает за данные, какие связи сохраняются и что можно удалить. Реализация этих правил остаётся задачей J3, J10 и J13.

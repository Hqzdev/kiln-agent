# Архитектура: как соединяются компоненты

Задача: A2.5. Дата: 11 октября 2026. Документы и настройки подготовлены; задача целиком требует реализации пользователя.

Программа собирает сервисы в одном месте — `CompositionRoot`. Сервисы получают нужные зависимости снаружи через интерфейсы. Такой подход называется внедрением зависимостей (DI). Он позволяет, например, заменить настоящий GigaChat тестовой моделью без изменения правил работы.

## Что подготовлено без кода приложения

Документ ниже описывает место соединения сервисов, нужные интерфейсы и способы замены компонентов. Добавленные ранее CompositionRoot, реализации хранилища и провайдера удалены. Папка backend/api/src/main/java/dev/blot/api подготовлена для пользовательской реализации. Наличие документа не подтверждает запуск сервера или проверку внедрения зависимостей; эти проверки выполняются после написания кода.

## Интерфейсы и реализации

| Интерфейс | Кто использует | В работающем приложении | В тестах |
| --- | --- | --- | --- |
| ProjectRepository / TaskRepository | Сервисы проекта | Хранилище JDBC | Хранилище в памяти с проверкой транзакций |
| ProviderGateway | Выполнение работы агентов | GigaChatAdapter | ScriptedProvider с заранее заданными ответами |
| ToolExecutor | Сценарий выполнения | ControlledMacRunner с ограничениями | RecordingExecutor, записывающий вызовы |
| GitGateway | Подготовка действий Git | Компонент Git с проверкой аргументов | StateMachineGitFixture, имитирующий состояния Git |
| ArtifactStore | Ревью и передача результатов | Локальное хранилище с адресацией по hash | FixtureArtifactStore |
| EventPublisher | Отправка сохранённых событий | Постоянный журнал событий | RecordingPublisher |
| Clock | Разрешения, расписания и повторы | Системные часы | FixedClock с заданным временем |
| DeviceTrustStore | Проверка отправителя API | Постоянное хранилище доверенных устройств | FixtureTrustStore |

Эти интерфейсы также называют ports. Их конкретные реализации — adapters.

## Создание сервисов

CompositionRoot выбирает настройки установки, хранилища, провайдера, исполнитель инструментов, часы и проверку устройств. Затем создаёт сервисы сценариев работы и контроллеры. Основной объект проекта или экран не должен создавать конкретную реализацию сам.

PolicyService передаётся во все пути выполнения инструментов. Проверка API определяет настоящего отправителя. Wi-Fi и посредник BLE вызывают одни сценарии работы: способ связи не выбирает другие правила доступа.

## Срок жизни компонентов

- Соединениями SQLite управляет код транзакций, а не агент.
- На один настроенный доступ к провайдеру есть одна GenerationQueue. Контекст каждой сессии хранится отдельно.
- Хранилище состояния экрана и текущий выбор могут жить столько же, сколько окно. Сама работа сохраняется независимо от окна.
- При выходе координатор в заданном порядке останавливает расписания, запросы и инструменты, затем записывает точку восстановления.

## Проверка замены компонентов

В тесте ScriptedProvider возвращает запрос инструмента и итог. RecordingExecutor подтверждает, что для одного commandId выполнена ровно одна операция. Тестовые часы позволяют проверить истечение разрешения без ожидания. Тестовое хранилище моделирует конфликт версий и отмену транзакции.

Замена провайдера или хранилища не требует наследования Agent и изменения контроллера. Тестовые реализации не подключаются к обычному запуску приложения.

## Когда A2.5 можно закрыть

Должен существовать CompositionRoot.java. Сервер должен запускаться с рабочими и тестовыми реализациями в нужных сценариях. В основных объектах не должно быть глобального поиска сервисов или скрытых одиночных экземпляров. Сейчас готово только описание этой структуры.

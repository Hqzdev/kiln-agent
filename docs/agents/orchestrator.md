# Оркестратор: жизненный цикл запуска

Документ описывает ответственность и поведение оркестратора Blot. Он фиксирует правила предметной области; наличие документа не означает, что соответствующая логика уже реализована.

## Назначение

Оркестратор управляет ходом одного `ProjectRun`: превращает цель и утверждённые требования в план, назначает работу профилям агентов, запускает сессии, собирает проверяемые результаты и проводит запуск через обязательные этапы приёмки.

Оркестратор координирует работу, но не заменяет отдельные роли. Менеджер проекта отвечает за план и назначения, исполнитель — за свою попытку, проверяющий — за независимое ревью, а пользователь — за решения и разрешения, которые нельзя делегировать агенту. Профиль роли и границы инструментов определяются каталогом агентов и [правилами инструментов](../tool-boundaries.md).

## Вход и результат

На входе оркестратор получает:

- идентификаторы проекта и запуска;
- цель пользователя и актуальную `SpecificationRevision`;
- доступные `AgentProfile` и их разрешённые возможности;
- действующие ограничения проекта и разрешения пользователя.

Результат работы оркестратора — сохранённый план, назначения и сессии агентов, история попыток и ревью, неизменяемые снимки результатов, журнал событий и итог запуска со ссылками на подтверждения и оставшиеся ограничения.

## Жизненный цикл

1. **Принять цель.** Проверить проект, запуск, версию требований и отправителя команды. Повторная доставка одного `commandId` не должна повторять действие.
2. **Подготовить план (G1).** Разбить цель на задачи с критериями готовности и зависимостями. Отклонить циклические зависимости и задачи без критериев. Сохранить версию плана и результат проверки. Если требования противоречивы или недостаёт решения пользователя, зафиксировать блокировку с конкретным вопросом. 
3. **Назначить задачи.** Выбрать профиль по роли, возможностям и области задачи. Учитывать зависимости, загрузку, ограничения запуска и необходимость независимого ревью. Сохранить основание назначения. Не создавать сессию для профиля, недоступного в этом проекте.
4. **Выполнить готовую работу (G2).** Запускать только задачи, чьи зависимости приняты. Передавать сессии минимум контекста, нужный для назначения. Все инструменты вызываются через серверные правила доступа. Сохранять попытку, операции и коды завершения; результат фиксировать неизменяемым снимком с hash и исходным `base SHA`.
5. **Провести независимое ревью (G3).** Назначить проверяющего, который не является автором проверяемой попытки. Связать решение и замечания с точным hash результата. При запросе исправлений создать новую попытку; предыдущее решение не переносить на новый hash.
6. **Объединить принятые результаты (G4).** Объединять только принятые результаты зависимых задач. Разрешение конфликтов и проверку общей версии фиксировать отдельной попыткой интеграции; не менять уже принятый снимок задним числом.
7. **Проверить качество и безопасность (G5).** Запустить обязательные для задачи проверки на точной версии объединённого результата. Хранить протокол с версией, командами и кодами завершения. Не считать отсутствующую проверку успешной.
8. **Выполнить разрешённые действия Git (G6).** Если цель включает commit или push, сначала подготовить точное действие. Исполнять его только при действующем разрешении пользователя и после проверки аргументов. Отказ или неизвестный исход сохранять явно.
9. **Завершить запуск (G7).** Завершить запуск только когда все обязательные задачи и gates пройдены на актуальных версиях. В итог включить выполненное, отклонённое, заблокированное, непроверенное и требующее решения пользователя; приложить ссылки на результаты и проверки.

## Состояния и переходы

Оркестратор хранит состояние запуска, а не выводит его из наличия открытого окна или активности модели.

| Состояние | Значение | Допустимое дальнейшее действие |
| --- | --- | --- |
| `draft` | Цель принята, план ещё не прошёл G1 | Подготовить или пересмотреть план |
| `ready` | План прошёл G1, есть готовые назначения | Начать доступные задачи |
| `running` | Выполняется хотя бы одна задача | Продолжить, отменить или зафиксировать блокировку |
| `blocked` | Требуется недостающее решение, зависимость или разрешение | Возобновить после устранения причины |
| `review` | Есть результат, ожидающий независимого ревью | Принять или вернуть на исправление |
| `completed` | Все обязательные gates пройдены | Только чтение и экспорт итогов |
| `cancelled` | Пользователь отменил запуск | Только чтение и экспорт сохранённой истории |
| `failed` | Запуск невозможно продолжить из-за неисправимой ошибки выполнения | Только чтение и разбор причин |

Переходы проверяются сервером по текущему состоянию и версии объекта. Команда с устаревшей версией отклоняется как конфликт, а не перезаписывает новое состояние. Остановка или сбой не удаляет уже сохранённые попытки и артефакты.

## Правила планирования и выполнения

- Параллельно запускаются только задачи без незавершённых зависимостей и без конфликтующей области изменений.
- Дочерние Motes запускаются только для независимой назначенной подзадачи; первый релиз ограничивает глубину одним уровнем и учитывает их расход в общем бюджете запуска. Stop, отзыв scope или исчерпание бюджета отменяет новые вызовы дочерней сессии; уже совершённые действия сверяются по журналу.
- Изменение требований создаёт новую ревизию и требует пересмотреть затронутые задачи и план. Результат нельзя автоматически считать соответствующим новым требованиям.
- Повтор создаёт новую попытку. Неудачные попытки, выводы и решения сохраняются для аудита.
- Агент может сообщить о блокировке или предложить изменение плана, но не может расширить собственные права, выдать себе разрешение, принять собственное обязательное ревью или выполнить действие вне выданного допуска.
- Передача сообщения другому агенту сама по себе не даёт ему новых прав.
- Ошибка провайдера, превышение бюджета или тайм-аута должны завершать операцию определённым состоянием и сохранять причину; бесконечные повторы запрещены.
- Все изменения состояния и соответствующие события сохраняются согласованно. Событие содержит идентификаторы проекта, запуска и команды, чтобы повторная доставка была идемпотентной.

## Блокировки и решение пользователя

Оркестратор переводит запуск в `blocked`, когда без внешнего решения нельзя безопасно продолжить: требования противоречат друг другу, нужен доступ за пределы разрешённой области, действие требует нового разрешения, отсутствует обязательный профиль или зависимость не может быть выполнена.

Запись блокировки содержит причину, связанные задачи, уже выполненную работу, конкретный вопрос или доступные варианты и условия возобновления. После ответа пользователя создаётся отдельная команда; история блокировки остаётся в запуске.

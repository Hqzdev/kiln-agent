# Архитектура: диагностические записи без секретов

Задача: A2.12. Дата: 11 октября 2026. Документы и настройки подготовлены; задача целиком требует реализации пользователя.

Логи помогают понять, почему произошла ошибка. Они должны сохранять полезный контекст и не раскрывать ключи или личные данные.

## Что подготовлено без кода приложения

В документе зафиксированы состав записи, уровни, ограничение размера, восемь файлов по 8 MiB и правила удаления секретов. LogRedactor, StructuredLogger и их тесты помощника удалены. Папка backend/infrastructure/src/main/java/dev/blot/infrastructure готова для пользовательского компонента. Секреты должны удаляться до записи и перед экспортом; отсутствие реализации нельзя считать выполненной защитой. Проверки stdout, stderr, файлов и экспорта выполняются после написания кода.

## Что содержит запись

Каждая запись включает время, уровень важности, часть системы, название события, длительность и код ошибки. При наличии добавляются ID установки, запуска, задачи и операции. Технические логи хранятся отдельно от пользовательской истории проекта.

Общие ID позволяют связать подтверждение команды, операцию инструмента, ревью и ошибку. Эти ID не являются ключами доступа и не отменяют проверку прав на проект.

## Что записывать запрещено

В логах не должно быть ключа GigaChat, токенов доступа, заголовков Authorization, секретов устройств, проверочного сообщения сопряжения, закрытых ключей подписи и полного секрета начальной настройки. Обычные ошибки не должны содержать необработанное тело сетевого запроса или переменные окружения процесса.

`LogRedactor` удаляет секреты до записи файла и до экспорта. Поля с секретами очищаются по структуре данных. Дополнительно проверяются известные маркеры тестовых секретов. Скрыть ключ только на экране недостаточно: его не должно быть в исходном логе.

## Вывод инструментов

У вывода есть лимит размера. Обрезанный вывод явно помечается `truncated`. Если исходный вывод нужен для подтверждения результата, он сохраняется как файл проекта с ограниченным доступом и контрольным отпечатком hash.

Личный текст проекта не должен попадать в общий диагностический экспорт без ограничения по проекту.

## Уровни записей

- Info — запуск, остановка и изменения состояния без секретных данных.
- Warning — повтор запроса, восстановление связи, обрезанный вывод и приближение к лимиту.
- Error — ошибка сценария работы или инфраструктуры с ID для поиска связанных записей.
- Debug — подробная диагностика, включаемая явно. Удаление секретов действует и в этом режиме.

## Размер и экспорт

Начальный лимит — восемь файлов по 8 MiB, как в [правилах хранения данных](../data-lifecycle.md). При заполнении старые диагностические файлы заменяются.

Описание диагностического экспорта содержит версии и контекст ошибки, но не содержимое Keychain. Перед передачей экспорт отдельно проверяется на секреты.

## Как проверить A2.12

Передать тестовый ключ через вход, ошибку инструмента и восстановление связи. Проверить стандартный вывод stdout, вывод ошибок stderr, файлы и экспорт.

Отдельно проверить заголовок Authorization, секрет в сообщении исключения и вывод переменных окружения. Полезные ID должны сохраниться, а секрет — исчезнуть. Пока описан только сценарий проверки; его реализация ещё предстоит.

# Backend Blot: реализация и границы готовности

Срез реализации: 21 октября 2026 года. Серверное ядро и системные адаптеры добавлены в репозиторий. **Полная приёмка всего плана ещё не завершена.** Ниже отдельно указаны реализованное поведение, доказательства проверок и оставшаяся интеграция.

## Решения владельца

- Выполнение программ переносится в отдельную VM macOS. Вложенный sandbox-exec на этом Mac не прошёл проверку. App Sandbox приложения остаётся включённым.
- Проверяем сервер, Swift-контракты и сборки Mac/iOS. Запуск упакованного приложения отложен: доступной Apple signing identity с приватным ключом нет, а ad hoc сборка JVM/JNI не прошла проверку Team ID при реальном запуске.
- Упаковка теперь требует `BLOT_SIGNING_IDENTITY`. Сборка исходников с `CODE_SIGNING_ALLOWED=NO` проверяется независимо от упаковки.

## Как читать код

Профессия агента задаётся `RoleCatalog`, `ProfileData` и снимком `AgentConfigurationData`. Подклассов для отдельных профессий нет. Тестовые модели и процессы существуют в `src/test`; обычный запуск выбирает реальные адаптеры.

## Реализованное поведение

### Данные и команды

SQLite работает с WAL, внешними ключами и короткими транзакциями. Строки принадлежат аккаунту; изменяемые записи имеют версию. Схема workspace обновлена до 8; wire-контракт остаётся v2. Перед обновлением создаётся согласованная `VACUUM INTO` копия, которая учитывает WAL. Копия получает уникальное имя `.before-v8-UUID` и становится готовой после сброса на диск и атомарного переименования.

`CommandDispatcher` сравнивает digest и `commandId`. Данные, квитанция и outbox фиксируются вместе. Повтор не исполняет действие заново. Старые HTTP-маршруты закрыты. Произвольного выставления статуса задачи или запуска в рабочем API нет.

Старые данные v1 доступны только после `legacy.adopt` на Mac с `confirmed: true`. Проект v2 получает отдельный неизменяемый архив прежних записей; прежние статусы не запускают агентов. Принятый исходный проект закрепляется за одним аккаунтом.

### Аккаунты и устройства

Argon2id, одноразовые коды, сроки, лимит попыток и задержка повторной отправки; реальные SMTP STARTTLS/implicit TLS; непрозрачные сессии с хешем в SQLite. Восстановление пароля отзывает прежние сессии. Сам токен и ключи хранятся в Keychain через закрытые pipes родительского Mac-приложения.

Сопряжение имеет срок, одноразовый секрет и отдельное подтверждение владельца. Секрет QR не попадает в журнал команд. Телефон получает свою сессию устройства. BLE использует отдельный TLS-коннектор; его loopback не считается локальным каналом владельца для регистрации и изменения секретов.

### Work, GigaChat и очередь

Сообщение и генерация сохраняются до модельного запроса. Потоковый текст сохраняется отдельно от статуса генерации. Остановка не превращает частичный ответ в завершённый.

HTTP adapter поддерживает OAuth, обновление токена, модели, подсчёт токенов, SSE, функции и usage. REST base URL по умолчанию — `https://api.giga.chat/v1/`. Ключ меняет digest доступа и сбрасывает использование прежнего кэшированного токена. Проверка TLS и имени сервера включена.

`SerializedProvider` сохраняет `MODEL_REQUEST`: назначение Work/Plan/Agent/Compaction, модель, владельца, время, состояние и приоритет. В первой версии приоритет обычных запросов равен 0, обслуживание — одна очередь на личный доступ. Позиция ожидания и активный вызов видны через records/events. Незавершённые записи после перезапуска получают INTERRUPTED. Два аккаунта с одинаковым внешним ключом используют общий semaphore по digest доступа; сами ключи и digest не выдаются в API. Смена ключа во время ожидающего или активного модельного запроса отклоняется.

`RetryingProvider` повторяет только определённые временные ошибки до начала текстового ответа, максимум три попытки. Бюджет резервируется перед каждой попыткой. Неизвестный usage учитывается консервативно и помечается как неизвестный.

### Контекст и память

`ContextBuilder` считает весь JSON запроса вместе с функциями, сохраняет место для ответа и запас. При 80% доступного входного бюджета запускает сжатие до 60%. Недавние обмены и пары вызов/результат остаются целыми. Старые сообщения сохраняются в БД.

`ContextCompactor` работает с закрытым диапазоном. Перед сохранением нового резюме проверяются версии исходных сообщений, памяти и предыдущего резюме. Ссылки на память переходят через повторные сжатия. Изменение или удаление записи инвалидирует все связанные резюме.

Память имеет пользовательскую, проектную, задачную и сессионную области. FTS5 фильтрует владельца, область и актуальность до ранжирования. «Запомни:» создаёт активную запись; отдельные явные формулировки предпочтений становятся кандидатами. Семантический автоматический разбор любой беседы пока не реализован: текущий извлекатель намеренно узкий.

`message.delete` отдельно удаляет исходное сообщение Work, проверяет отсутствие активной генерации, инвалидирует затронутые резюме и помечает производные записи памяти устаревшими. Полное удаление самой записи памяти — отдельная команда. Кэш результата команды очищается при явном удалении ресурса; ID и digest команды остаются для защиты от повторения.

### Code, специалисты и Motes

План проверяется на критерии принятия, роли, области, DAG и покрытие структурированных требований. `requirements` перечисляет требования, `coverage` связывает каждый ключ с существующими ключами задач. После принятия сохраняется карта фактических taskId; неподтверждённое или неполное покрытие отклоняется. Существенный вопрос создаёт сохранённую контрольную точку с тремя вариантами и собственным ответом. Уточнение создаёт новую ревизию требований, прежние попытки остаются в истории.

Планировщик создаёт отдельные сессии и рабочие области. Конфигурация каждой сессии заморожена. Mote ограничен глубиной 1, областью родителя, ролью, инструментами и общим бюджетом запуска. Отмена родителя прекращает новые действия ребёнка. Входящие сообщения подтверждаются после обработки и ограничены по объёму.

Агентный цикл вынесен в небольшие сервисы: сбор контекста → поток модели → проверенный инструмент → сохранённый результат. Частичный JSON функции не исполняется. `ToolHistory` восстанавливает пропущенный результат после сбоя; сообщения коллегам и вопросы имеют ID исходного вызова, поэтому восстановление не отправляет их повторно.

### Инструменты, ревью и Git

Файловые операции проверяют фактические пути, символьные ссылки и `.git`. Подготовленное изменение связывает аргументы, исходный коммит и hash. Разрешение потребляется атомарно, повторно проверяется перед действием и во время ожидания VM. Неизвестный исход блокирует новые побочные эффекты и завершение задачи.

Reviewer проверяет неизменяемый артефакт и его hash. Интегратор получает принятые результаты. Сервер добавляет финальные QA и security этапы; QA требует настоящего exitCode 0, security — зафиксированного чтения исходников. Само сообщение модели «готово» не завершает запуск.

Commit и push готовятся и разрешаются отдельно. Commit проверяет дерево и исходный ref; push отправляет точный SHA, проверяет URL/refspec и фактическую основную ветку удалённого репозитория. Репозиторные hooks, filters и произвольные credential helpers не запускаются на основном Mac. Настройка реальной аутентификации выбранного remote и приёмка настоящего push ещё требуют проверки.

### VM и доступ к папкам

Добавлены установка гостевой macOS, интерактивная подготовка инструментов, копирование базового образа, гостевой runner и проверка переноса файлов. Командные VM не получают сетевого устройства. В гостя передаётся staging, без исходного `.git`, БД, Keychain и настроек приложения. Перед импортом результатов VM полностью останавливается. Изменения разрешены только в назначенных путях.

VM не проверена настоящим запуском подготовленного образа. Это ограничение приёмки, а не подтверждённая работоспособность профилей Gradle/Xcode. При неподготовленной среде возвращается ошибка.

Выбор репозитория добавлен в Settings → Git & GitHub. `ProjectBookmarks` и Foundation JNI adapter открывают системный доступ внутри Java. После перезапуска доступ восстанавливается по bookmarks. Сборка JNI подтверждена; поведение в подписанном App Sandbox требует отложенной проверки приложения. [Описание](architecture/project-folder-access.md), [VM](architecture/virtual-machine-runner.md).

### Хранение и расписания

Артефакты имеют SHA-256, читаются частями с проверкой hash. ZIP экспорт включает манифест и сами результаты. Диагностический экспорт содержит метаданные, без промптов и секретов. Очистка удаляет только старые blobs без ссылок, с защитой недавно переиспользованного содержимого.

Удаление проекта сохраняет задания `WORKSPACE_CLEANUP` до окончания файловой очистки. Повтор переживает перезапуск. Подготовка рабочей области блокирует удаление проекта до завершения; основная папка, пользовательские несохранённые изменения, другие запуски и созданные ветки не удаляются. Symlink не позволяет выйти из служебной папки.

`GET /v2/statistics` возвращает известные токены, незавершённые запросы, состояния запусков/задач, ревью и замечания. Неизвестный usage помечается отдельно, цена остаётся null без подтверждённого тарифа.

Навыки версионируются и не выдают права. Расписания используют timezone и устойчивый ID «автоматизация + запланированное время». После сна создаётся максимум один запуск, событие отмечает объединение пропусков. Проверена повторная доставка после сбоя и перевод часов.

## Проверки

### Подключение экранов Mac

Code, Motes, граф, навыки и расписания используют записи API v2. Прежние демонстрационные наборы этих экранов удалены. `LiveWorkspace` получает snapshot и SSE, перечитывает изменённую запись и проверяет владельца и версию. Его клиент передаётся через конструктор; этот же код исполняется в Swift-тестах без запуска приложения.

- Новая задача и командный запуск вызывают `run.create`. План, требования и критерии доступны до `run.plan.approve`. Пауза, продолжение, остановка, уточнение и принятие результата вызывают соответствующие команды сервера.
- Команда показывает реальные сессии и Motes, состояния ожидания, каналы сообщений и сохранённую переписку агентов. Вопросы и точные подготовленные действия принимают ответы пользователя через v2.
- Результаты показывают артефакты, hash независимого ревью, замечания и результаты инструментов. Commit и push отдельно готовятся, разрешаются и исполняются. При неизвестном исходе доступна сверка с сервером.
- Три режима графа строятся по реальным задачам, назначениям, зависимостям, сессиям, сообщениям и ревью. Узел и связь открывают запись-источник; одинаковая роль двух сессий не объединяет их в одного агента.
- Навыки создаются, изменяются, включаются и удаляются на сервере. Роли загружаются через `/v2/roles`. Настройки инструкций и разрешений ведут к настоящим навыкам и подготовленным действиям.
- Расписания сохраняют дни недели, время, timezone и бюджет. «Запустить сейчас» создаёт обычный запуск. История содержит сохранённые ссылки на фактические запуски; повтор команды не создаёт второй запуск.
- Команды после обрыва сохраняют исходный ID и payload. При входе выполняется восстановление очереди; до его окончания новые команды заблокированы. Выход и смена аккаунта очищают кэш, выбор, историю навигации и локально прикреплённые источники.

В проверке SSE исправлено чтение разделителя событий: используется ограниченный разбор байтов с поддержкой LF/CRLF и многострочного data. Тест подтверждает весь путь snapshot → SSE → GET изменённой записи → обновление наблюдаемого состояния.

Существующий интерфейс не запускался для визуальной проверки по решению владельца. [Подробный срез подключения](verification/mac-backend-binding-2026-10-21.md).

Набор включает:

- Реальный HTTP сервер, SQLite, авторизацию, повтор команд, разделение аккаунтов и закрытие v1.
- Настоящий TLS сервер и разделение локального/BLE-коннектора.
- Управляемый агентный сценарий: план → принятие → исполнитель → reviewer → интегратор → QA с разрешением процесса → security → принятие результата.
- Motes: область, глубину, родительский бюджет и отмену родителя.
- Контекст: целевой размер, сохранение исходников, целостность функций и наследование источников памяти.
- Временные Git-репозитории: фильтры, защищённые ветки, неизменяемый commit и точный push в локальный bare remote.
- HTTPS fixture GigaChat: OAuth, смену ключа, фрагменты function_call и usage.
- Временный тестовый CA: доверие одного аккаунта и сохранение проверки имени сервера. Внешний CA в сборку автоматически не добавлен.
- Очередь модели: сохранённое ожидание, один активный вызов общего доступа двух аккаунтов и восстановление после сбоя.
- Артефакты, GC, старую схему, источники истории и расписания.
- Swift DTO v2, Int64, Bluetooth frames и ответ настоящего Java HTTP fixture.

## Что ещё нужно для полной готовности приложения

1. Провести визуальную и пользовательскую проверку подключённых экранов Mac после разрешения запуска приложения. Подключение Code, команды, графа, навыков и расписаний реализовано и проверяется без запуска UI; этот результат не заменяет проверку интерфейса в работающем приложении.
2. Провести реальный SMTP и GigaChat сценарий с доступом владельца. Нужен доверенный CA НУЦ для GigaChat: предусмотрен ручной выбор PEM, просмотр SHA-256 и отдельное подтверждение в приложении. Автоматическое добавление внешнего root CA в сборку было отклонено проверкой разрешений из-за изменения доверия без подтверждённого отпечатка; загрузка и добавление не выполнены.
3. После настройки signing identity проверить полный запуск упакованного приложения и доступ к выбранному репозиторию. Этот запуск отложен владельцем.
4. Подготовить VM, JDK/Gradle, Xcode и кэши зависимостей. Провести реальные проверки обоих профилей, отмены, времени выполнения и импорта файлов.
5. Проверить Wi-Fi/BLE и переключение транспорта на физическом iPhone, отзыв устройства и восстановление после сна/перезапуска.
6. Пройти весь финальный сценарий из product-scope, включая исправление после ревью и отдельные разрешения commit/push. Смысловую полноту извлечённых требований пользователь проверяет перед принятием плана; сервер проверяет формальное покрытие всех перечисленных требований.

Дополнительно: история событий пока хранится без автоматической временной очистки; сервер не обещает ограниченную дисковую ретенцию. Очередь использует одинаковый приоритет 0, отдельный пользовательский выбор приоритетов не добавлен. Телефон показывает данные подготовленного Git-действия и разрешает его, но отдельные элементы подготовки и исполнения commit/push на телефоне ещё не подключены.

Этот документ фиксирует фактическую готовность. Сборка и успешные fixture-проверки не заменяют оставшуюся приёмку.

# Kiln: как разговор становится заданием

Задача: P0.3. Дата: 11 октября 2026.

## Обсуждение и работа

В режиме разговора пользователь задаёт вопросы и уточняет идеи. Ответ модели сам по себе не разрешает менять файлы, запускать программы или выполнять команды Git.

В режиме работы пользователь просит сделать что-то конкретное. Руководитель записывает цель, проект, ограничения и ожидаемый результат. Затем создаёт рабочий запуск (`ProjectRun`) и план, по которому можно проверить готовность.

## Когда начинается работа

| Сообщение или ситуация | Что происходит |
| --- | --- |
| «Как лучше построить API?» | Ответ в чате; работа не запускается |
| «Реализуй этот API в выбранном проекте» | Обработка команды create_run, сохранение версии требований и плана |
| Цель есть, но проект не выбран | Пользователь выбирает проект; инструменты пока не запускаются |
| Не хватает важного условия | Уточняющий вопрос в том же чате; черновик сохраняется |
| Пользователь уточнил текущую задачу | Требования получают новую версию; менеджер оценивает, нужно ли менять план |
| Пользователь отменил уточнение | Черновик остаётся в истории; выполнение не начинается |

Если просьба неоднозначна, система уточняет её или показывает предварительный план. Фактическое начало работы отмечается событием `run.started`. Интерфейс показывает выбранный репозиторий и активный запуск.

## Команды API

- `conversation.send_message` — отправить сообщение без запуска работы.
- `run.create` — передать цель, projectId, вложения и ограничения. Обязателен commandId — уникальный номер команды.
- `run.answer_clarification` — ответить на вопрос clarificationId и указать ожидаемую версию данных expectedVersion.
- `run.steer` — дополнить или скорректировать указания для активного запуска.
- `run.pause`, `run.resume`, `run.stop` — приостановить, продолжить или остановить работу.

Сервер определяет отправителя по проверенному подключению. Повтор `run.create` с тем же commandId возвращает прежнее подтверждение приёма команды и не создаёт второй запуск.

## Что видно во время работы

Пользователь видит общий чат руководителя, каналы специалистов, план, текущую задачу, настоящий вывод инструментов и причины остановок. Сообщение одного специалиста другому не считается новым заданием пользователя.

На iPhone действуют те же правила. Без связи текст остаётся черновиком. После отправки интерфейс различает три этапа: команда отправляется (`sending`), сервер принял её (`acknowledged`), работа выполняется. Телефон не запускает инструменты у себя.

## Разрешения

Режим работы разрешает составить план в пределах цели пользователя. Действия, которые меняют файлы или внешние системы, проходят [отдельную проверку разрешений](permission-policy.md). Обычный ответ в чате не должен скрыто приводить к commit или push.

## Как проверить эти правила

1. Вопрос об архитектуре даёт ответ и не создаёт операций инструментов.
2. Явное задание создаёт ровно один запуск и одну версию требований.
3. Уточнение обновляет требования, но исходный запрос остаётся в истории.
4. Повтор после сетевого тайм-аута не создаёт вторую команду.
5. Остановка сохраняет частичный результат и не начинает следующие операции.
